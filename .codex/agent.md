# 项目协作总领（Agent Guide）

本文件是参与本项目开发的智能体与开发者的协作入口。项目当前处于初始化阶段；业务目标、技术栈和部署方式尚未确定，除非在文档中明确记录，不应把推测当作架构事实。

## 每次开发前

按以下顺序阅读：

1. `docs/README.md`：了解文档入口和当前状态。
2. `docs/architecture.md`：确认当前架构、边界和约束。
3. `docs/development-plan.md`：确认本次工作对应的计划、优先级和验收标准。
4. 与当前任务相关的 `docs/decisions.md`、`docs/discussions.md` 及其他文档。

如果实现过程中发现文档与代码不一致，先判断是代码问题还是文档过期；不要默默绕过架构约束。

## 实施规则

- 先说明目标、影响范围、假设和验证方式，再开始修改。
- 保持模块职责清晰，避免为了短期便利引入跨层依赖、隐式全局状态或重复配置。
- 发现会影响模块边界、数据流、公共接口、持久化、部署或安全性的变化时，必须先在 `docs/decisions.md` 记录决策，再实现。
- 一次提交尽量只解决一个清晰的问题；与任务无关的重构单独提出。
- 新增代码应配套必要的测试、错误处理和文档；不能验证的假设要明确写成待办。

## 实施完成后

完成代码后按以下顺序收尾：

1. 运行与改动相关的测试、检查或构建，并在交付说明中记录结果。
2. 若架构、接口、流程或约束发生变化，立即同步 `docs/architecture.md`。
3. 若形成了取舍或不可逆选择，追加一条 `docs/decisions.md` 决策记录。
4. 更新 `docs/development-plan.md` 中的状态、验收结果和后续工作。
5. 将重要讨论结论补入 `docs/discussions.md`，不要只留在聊天记录里。

## 文档维护约定

- 文档描述“当前有效状态”；历史取舍放在决策记录中，不要用大段过时内容污染当前架构说明。
- 使用明确的 `TODO`、`TBD` 或 `待确认` 标记未决事项，并注明负责人或下一步。
- 变更文档时保持标题和链接稳定，便于后续检索。
- 代码与文档冲突时，以经确认的最新决策为准，并在同一变更中修正文档或代码。

## 交付检查清单

- [ ] 已阅读本文件及 `docs/README.md`。
- [ ] 已确认任务对应的架构边界和计划项。
- [ ] 已完成必要的测试、构建或静态检查。
- [ ] 已同步架构、决策、讨论和计划文档（如适用）。
- [ ] 已说明未完成项、风险和后续建议。
